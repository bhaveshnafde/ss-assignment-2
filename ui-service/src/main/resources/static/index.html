Challenge 1 · A contended resource is never over-allocated

Many requests try to take money from the same account at the same moment. Without care, they all read the same balance, all pass the check, and the account goes negative. Here a fresh account is opened, then all requests are fired at once. Each one asks to set money aside (a hold). The Account service uses one conditional SQL UPDATE (… WHERE available >= amount), so exactly as many succeed as the balance allows.

Challenge 2 · Sending money is safe to repeat

The customer's app may send the same request twice: a timeout, a retry, a double click. Each transfer carries an Idempotency-Key. The Transfer service claims the key with a database primary key and remembers the answer, so a repeat gets the same answer and no money moves twice. Each scenario opens a fresh account with ₹1,000 and sends to ACC-1001.

A · Retry after a lost answer

Send ₹100, then send exactly the same request with the same key.

B · Double click: identical requests at the same moment

Fire identical requests with one key, all at once.

C · Same key, different request

Send ₹100, then reuse the key for ₹200. The second must be refused.

D · No key at all

A transfer without an Idempotency-Key header is refused before anything happens.

Challenge 3C · A failure halfway is undone

A transfer touches four databases, so it cannot be one transaction. Transfer runs a saga: 1 reserve the limit, 2 hold the money, 3 post the ledger journal, 4 capture. Here the Ledger is made to fail, so step 3 fails after its retries. Transfer must then undo steps 2 and 1 in reverse order and leave nothing reserved.

A dependency that can be slow or fail

The SMS provider is simulated by our Notification service and can be made slow or failing. Transfer sends the SMS in the background after the transfer is COMPLETED, and retries when the provider fails. A failed SMS never fails a transfer, and the same transfer is never notified twice.
